From idea to review, without the handoffs

Shipping a feature usually means repeating context across planning, coding, testing, Git, and pull-request tools. /ship turns those handoffs into one small, visible pipeline. You describe the outcome once; Quark carries that context through the delivery lifecycle.

It is intentionally not a general-purpose workflow builder. The sequence is fixed, easy to understand, and designed around the job developers do today: plan, implement, verify, and publish.

1

Plan

The Oracle explores the project and produces a minimal plan with Gherkin acceptance criteria.

2

Implement

A coder works from that plan inside a dedicated Quark worktree.

3

Verify

A fresh verifier inspects the result and runs relevant project checks.

4

Publish

Quark commits, pushes, and opens a draft pull request for review.

Autonomous does not mean invisible

A persistent Ship card stays in your Quark conversation throughout the run. It shows the current phase, active agent, attempt number, duration, branch, worktree, and the final pull-request URL. You can see where the work is and what happened without exposing hidden model reasoning.

Isolated by default

Every run gets a dedicated ship/* branch and a worktree under .quark/worktrees/.

Acceptance-led

The plan includes behavior-focused Gherkin criteria that travel from planning into verification.

Bounded repair

If verification fails, the same coder receives the short reason and can repair the work—up to three total attempts.

Recoverable failure

If the run cannot pass or publish, Quark preserves the branch, worktree, session, and diagnostic state.

A verifier that starts fresh

Implementation and verification have different jobs. The implementation agent keeps its session across repairs so it retains context. Each verification uses a fresh session, receives the original request and acceptance criteria, and judges the actual worktree instead of trusting the implementation summary.

When verification fails, it returns one short reason. Quark sends that reason back to the existing implementation session, then asks a new verifier to check the repair. The loop stops as soon as the feature passes, or after three implementation attempts.

Start with the feature, not the ceremony

There are no workflow flags to learn. Give /ship one clear feature request:

› /ship add keyboard navigation to the model picker

A useful request names the user-visible outcome and any important constraint. Quark and the Oracle discover the relevant files and turn the request into an implementation-ready plan.

Safe cleanup, useful failures

Quark only removes the worktree and temporary run artifacts after verification passes and the pull request has been created. If planning, coding, verification, pushing, or PR creation fails, the work stays available for inspection and manual continuation.

Cleanup trouble never hides a successful shipment. If the PR exists but a local artifact cannot be removed, Quark reports a warning and keeps the successful PR result.

Before you run /ship

The first release expects:

  • a Git repository with an origin remote;
  • GitHub CLI installed and authenticated with gh auth login;
  • configured oracle and coder Quark profiles; and
  • a clean enough project setup for the verifier to run relevant checks.

Less coordination. More review-ready work.

/ship gives Quark a clear finish line: not “write some code,” but “deliver a verified change that is ready for human review.” It keeps the workflow minimal, the progress visible, and failures recoverable.
